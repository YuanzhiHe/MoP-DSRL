## 2. What was never recorded

These fields do not exist in any stored artifact and cannot be recovered:

- per-bin raw counts of either the policy histogram or the reference (only the
  normalised `C_phi` and `C_ref` were written);
- the number of valid-labelled and total evaluation episodes per run;
- the number of reference chunks that failed or were dropped;
- checkpoint, configuration or reference hashes;
- the code commit each run executed under;
- the fine-tuned noise policies themselves - `run_d3il_headtohead.py` contains
  no `torch.save`, so no run's learned policy survives.

The last item settles what reanalysis can and cannot fix. Re-evaluating a past
run is impossible: only the frozen backbone survives, not what was trained on
top of it. Any endpoint that was computed wrongly at evaluation time has to be
regenerated by rerunning, not recomputed.

Per-bin counts are a partial exception. The stored probabilities are ratios of
small integers, so counts can be recovered by rationalising `C_phi` against the
evaluation budget recorded in the launch command. This is reconstruction, not a
record, and it is marked as such in the manifest.

## 3. Manifest

`scripts/v2/build_manifest.py` writes `runs/_d3il_v2/manifest_legacy.jsonl`,
one record per planned cell, 4821 records. It joins each job's parsed command
line to the rows that job wrote. Fields never recorded are emitted as `null`
rather than guessed. `code_commit` carries the commit at reconstruction time
with `code_commit_is_run_time: false`, because the run-time commit is unknown.

## 5. Reconciling "38 frozen policies and 1,235 fine-tuning runs"

38 frozen policies is confirmed: 20 Avoiding and 18 Pushing carry completed
cells.

1,235 is not reproducible. Counts available under defensible rules:

| Rule | Count |
|---|---|
| Deduplicated rows over the manuscript's own file set, the loader's key | **1,237** |
| Main cohort only, both tasks, no penalty-weight sweep | 953 |
| Completed cells over all sweeps, counted per job | 2,554 |
| All rows in all files, deduplicated | 2,640 |

No combination of files, filters or dedup keys produces 1,235, and the nearest
is 1,237 under the rule the analysis scripts themselves apply. `verify_readme.py`
appears to check this figure but only tests that the string "1,235" occurs in
both the README and the manuscript; it never recomputes it.

## 6. Failures and abnormal exits

- 28 jobs ended abnormally: 853 planned cells inside jobs that hit the SLURM
  time limit, 445 inside jobs that raised.
- 8 jobs died during `import torch` with `OSError: [Errno 5] Input/output
  error`, a filesystem fault, before writing a command line. Four of them
  (`R050_*`) were the Pushing penalty-weight 0.50 resume jobs.
- 13 rows carry an explicit `failed` key.
- 2,267 planned cells have no row. This figure is inflated: jobs launched with
  `--resume` replan cells that earlier jobs already completed, and the manifest
  counts a cell once per job that planned it.

## 7. Confirmed implementation defects

Each reproduced against the code at `scripts/run_d3il_headtohead.py`.

**Rewarded success is computed on the wrong label space.** Training rewards
`info["mode_id"] in rewarded` on the raw 24-route id, correctly. Evaluation
coarsens first and then tests membership of the raw id set:

```python
modes = np.asarray([coarsen(m, K) for m in modes])   # 24 routes -> 6 groups
rewarded_SR = np.mean([m in rewarded for m in modes[valid]])
```

For Avoiding a reported hit requires a drawn route id below 6 that also equals
a coarse group index. Across the 18 seeds used, 6 have no drawn id below 6 at
all, so their reported rewarded success is pinned at 0 by construction; the rest
can register at most one of their four rewarded routes. The quantity is also
conditional on a valid label and ignores `success` entirely, so it is not a
success rate. The same line appears in both `run_arm` and `run_bmd`.

**The JS coefficient carries a spurious constant.** The code uses
`-(0.5*log(p/m) - 0.5)`; the derivative of JS is `0.5*log(p_k/m_k)`. The extra
term is applied only to trajectories that carry a valid label, so it does not
cancel as a baseline, and the batch centring that follows does not remove it
either, because invalid trajectories hold 0 rather than the same constant.

**The two objective terms are standardised separately.** `adv` is divided by its
batch standard deviation and `mode_coef` by its own, then combined as
`adv_n + lam*mode_coef`. The effective weight is therefore
`lam * sd(adv)/sd(coef)`, which varies batch to batch, so no fixed
reward-minus-penalty objective corresponds to the update.

**Conditional centring is not the conditional gradient.** Invalid trajectories
are assigned coefficient 0 and the whole batch is then centred. For an endpoint
defined as `P(mode = k | valid label)` the population coefficient is
`V/s * (g_mode - sum_k C_phi[k] g_k)`; subtracting the batch mean of a vector
that holds 0 on invalid entries is a different quantity, and `s` is never
estimated. The EMA is also updated with the current batch before that same batch
uses it, so the estimate is not lagged.

**The reference is chosen by majority after filtering.** `unify_reference()`
picks, within a group, the `C_ref` carried by the most surviving rows and
rescores the others against it.
